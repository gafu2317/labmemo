# SG-USM 日本語読解ノート

PDF: [07_SG_USM_2023.acl-long.116.pdf](../pdfs/07_SG_USM_2023.acl-long.116.pdf)  
原題: Schema-Guided User Satisfaction Modeling for Task-Oriented Dialogues  
著者: Yue Feng et al. / ACL 2023

## 一言まとめ

タスク指向対話の**ユーザ満足度（USM）**を、「タスクスキーマ上の属性（slot）がどれだけ満たされたか」と「各属性の重要度」から計算するモデル。  
今回の実験における **Task Success / Goal Fulfillment の考え方を、そのまま流用できる**。

## Abstract / 導入の要点

- タスク指向対話の評価では、BLEU などの自動指標があまり機能しないため、  
  **User Satisfaction Modeling (USM)** が注目されている。
- 著者らは、「ユーザ満足は、タスクスキーマに定義された**属性（task attributes）ごとの充足度**に依存する」という立場を取る。
  - 例: レストラン検索なら `City`, `Price_Range`, `Food` など。
- SG-USM の構成:
  - BERT で
    - 対話履歴（ユーザ+システム発話）
    - タスク属性（スロット記述）
    をエンコード。
  - **Task Attribute Fulfillment Layer**:
    - 各属性に対して、対話中のどの発話がその属性の充足に関係するかを Attention で表現。
  - **Task Attribute Importance Predictor**:
    - 多数の対話から「どの属性が重要か」を推定（出現頻度 + 位置ディスカウントなど）。
  - 充足度ベクトル × 重要度ベクトル → 集約して MLP に入れ、満足度クラス（満足/中立/不満など）を予測。
- MultiWOZ / SGD / ReDial / JDDC など複数データセットで、既存USM手法より高性能。

## Abstract 日本語訳（意訳）

ユーザ満足度モデリング（USM）は、タスク指向対話システムの評価としてよく使われる。通常、ユーザ満足は「ユーザのタスク目標がシステムによってどれだけ満たされたか」に大きく依存する。タスク指向対話システムではタスクスキーマ（task schema）を使って目標を表し、スキーマはタスク属性（task attributes）の集合である。しかし既存研究では、スキーマに基づいて「各属性の充足度合い」を明示的にモデル化して満足を予測することが十分ではなかった。そこで著者らは SG-USM を提案する。SG-USM は、ユーザが属性ごとの好み（属性と値のペア）をシステムがどれだけ満たしたかを明示的に表現し、その充足度合いと属性の重要度を使って満足度を予測する。具体的には、BERT で対話コンテキストとタスク属性を表現し、各属性の充足を推定する層と重要度推定モジュール、そしてそれらを使って満足度を予測するモデルから成る。MWOZ / SGD / ReDial / JDDC などで、既存手法より一貫して優れることを示している。

## 何が近いか（今回の実験の Task Success 設計）

- 借り手エージェントの「タスク成功」を、単に1ビットではなく
  - 例: `家賃上限`, `立地`, `広さ`, `駅徒歩`, `築年数`, `その他希望`
  のような **スロット集合（task attributes）ごとの充足度**として見る、という発想がそのまま合う。
- 設計書で出てきた **YAML の `slots`** を、「SGD におけるスキーマ属性」として解釈できる。
  - 各スロットの `fulfilled / partially / unmet` を付けておき、  
    タスク成功スコアを「重要度付きの充足度合計」として定義するのは SG-USM と同じ構造。

## 今回への示唆（構造化 vs Baseline の比較観点）

- **構造化プロンプトの利点を「スロット充足のしやすさ」で語れる**:
  - 構造化条件では、「どんなスロットが存在するか」「どの値が希望か」を Borrower LLM に明示するため、
    - 適切な質問を投げる、
    - 条件外の物件を早期に排除する、
    などがしやすくなり、**重要スロットの充足率が上がる**と期待できる。
- 実験結果の読み方:
  - 全ケースで単一の「成功/失敗」ではなく、
    - `slots` ごとの充足ベクトル
    - 重要度（今回なら、ユーザが事前に付けた重み or 手動ラベル）
  を残しておくと、「構造化プロンプトは特にどの属性の達成を助けたか」を分析できる。

## 発表で使える一言

SG-USM は、「ユーザ満足はタスク属性ごとの**充足度 × 重要度**で決まる」という立場から USM を設計している。  
借り手エージェントの実験でも、YAMLで定義した `slots` をタスク属性とみなし、**構造化プロンプトが重要スロットの達成率をどこまで押し上げるか**を、この考え方で評価できる。
